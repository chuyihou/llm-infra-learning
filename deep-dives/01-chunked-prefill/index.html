Chunked Prefill：把长 Prompt 变成可调度的工作

Chunked Prefill 不是一种新的 Attention，也不是把上下文切断。它做的事情更朴素：不再要求一个长 Prefill 一口气跑完，而是在安全的边界上把执行权还给 Scheduler。

这篇文章回答什么为什么长 Prompt 会干扰在线 Decode；切块以后模型语义为什么不变；开启它会让谁变快、让谁付出代价；以及 SGLang 里状态、预算和参数怎样对应。

面向谁了解 Transformer 与 KV Cache、关心 TTFT、ITL、吞吐、显存和调度实现的 Infra 工程师。

代码基线SGLang c19dc43 · vLLM 4edb551，核对日期 2026-09-22。

一句话先记住：Chunked Prefill 优化的不是“总共算多少”，而是“多久把一次重新排班的机会还给系统”。

01 / WHY

为什么需要 Chunked Prefill

根因不只是“长 Prompt 很慢”。Prefill 与 Decode 以完全不同的方式使用 GPU，而在线调度又必须同时照顾新请求的首 token 和已有请求的流式输出。

1. Prefill 与 Decode，把 GPU 推向相反的瓶颈

Prefill 一次处理 Prompt 中的许多 token。在线性层里，输入可以看成 [L, H]，其中 L 是本轮 Prompt token 数，H 是 hidden size；它与权重矩阵相乘形成较大的 GEMM。随着 L 增大，同一份权重可以被更多 token 复用，矩阵乘法的算术强度升高；与此同时，self-attention 的计算量还随序列长度近似按 L² 增长。达到硬件 roofline 的转折点后，Prefill 通常从没有充分利用计算单元，走向更明显的 compute-bound。

Decode 每条序列每轮通常只生成一个 token。小 batch 时，线性层更像 GEMV 或很瘦的 GEMM：为了很少的计算，仍要读取大量模型权重；attention 还必须读取此前全部 KV Cache。上下文长度 S 越长，每个新 token 需要读取的 KV 越多，因此 Decode 通常先受到 HBM 带宽约束，也就是 memory / I/O-bound。[1]

每生成 1 个 token 的 KV 读取量（近似）
2 × Nlayers × S × Nkv_heads × dhead × byteselement前面的 2 表示 K 和 V；公式忽略缓存层级、分页与 kernel fusion，只用来理解为什么读取量随上下文 S 线性增长。
不要把“token 变多”混成一件事

Prefill 中增加的是本轮同时计算的 Query 数；Decode 中增加的上下文 token 主要扩大每个 Query 必须读取的 KV 历史。

更长上下文本身不会让 Decode 自动 compute-bound

它通常让 Decode 更受带宽限制。让 Decode 趋向 compute-bound 的常见变量是更大的 batch、更多并行 token 或能显著增加数据复用的 kernel。

2. TTFT 与 ITL：同一块 GPU 上的目标冲突

TTFT（Time To First Token）衡量新请求从到达到首 token 的等待；ITL（Inter-Token Latency）衡量流式输出中相邻 token 的间隔。对新请求而言，Scheduler 越早运行完整 Prefill，TTFT 越好；对已经 Decode 的请求而言，这个重而长的 forward 会延后下一轮 Decode，造成 ITL 尖峰。

问题的关键不是平均 ITL，而是波动。用户会直接感知流式输出突然停顿；即使平均 tokens/s 没有明显变化，一次偶发的长 Prefill 也可能把 p95/p99 ITL 拉高。反过来，如果永远优先 Decode，新到的长 Prompt 会持续排队，TTFT 又会恶化。

ADDITIONAL READING次要背景：TP 受通信约束，PP 受 bubble 约束多卡部署与 Pipeline bubble 的补充背景

当单卡放不下模型时，Tensor Parallelism（TP）和 Pipeline Parallelism（PP）会把问题带到多卡。它们的主要压力不同，这也决定了 Chunked Prefill 可能影响哪里。

Tensor Parallelism

把同一层的矩阵切到多张卡。几乎每层都需要 All-Reduce、Reduce-Scatter 或 All-Gather，因此对卡间带宽和 collective latency 非常敏感；TP degree 越大，通信越容易进入关键路径。

Pipeline Parallelism

把不同层放到不同 stage，只在 stage 边界传 activation；但 stage 必须等待上游 microbatch。启动、排空和各 stage 耗时不均都会产生 pipeline bubble，也就是 GPU 有资源却没有可执行工作。

02 / CORE MECHANISM

Chunked Prefill 的核心原理

完整机制包含三层：把 Prefill 变成可续跑的 chunk；把 chunk 与 Decode 组成 mixed batch；再根据长上下文成本和 PP stage 节拍调整 chunk。

1. 把完整 Prefill 切成更小的 Chunk

设 Prompt 长度为 L，单个 chunk 上限为 C。不切块时，Scheduler 一次提交 [0,L)；切块后，它依次提交 [0,C)、[C,2C)，直到 Prompt 完成。因此，一个 Prompt 大约需要 ceil(L/C) 次 Prefill iteration。

这不是把一条 message 变成几个彼此无关的小 Prompt。第一个 chunk 处理完成后，它产生的 K/V 会进入 KV Cache；第二个 chunk 只为新 token 生成 Q/K/V，但新 Query 仍然可以读取完整前缀的 K/V。中间 chunk 不应该提前采样，只有完整 Prompt 被处理后才开始正常 Decode。

为什么切开以后模型语义仍然成立

以第二个 chunk T4…T7 为例。它虽然只为四个新 token 生成 Query，但每个 Query 的 Key/Value 可见范围仍由原始全局位置决定。Q7 可以读取 K0…K7，而不是只能读取 K4…K7。要保证这种等价性，实现必须同时维护三个不变量。

KV 连续追加展开例子

第二轮不重算 T0–T3；它读取历史 KV，并把 T4–T7 的新 KV 接到后面。

KV 0–3→KV 4–7

假设 chunk_size=4。物理 KV page 可以分散，但逻辑上的 token 顺序不能改变。

ITERATION 1
写 KV0写 KV1写 KV2写 KV3
ITERATION 2
读 KV0读 KV1读 KV2读 KV3写 KV4写 KV5写 KV6写 KV7

检查点：第二轮结束后，逻辑缓存覆盖 KV[0:8)；只是分两轮建立，并非两条序列。

Position 不重置展开例子

Chunk 只是执行边界。第二轮的 T4 仍位于全局位置 4，而不是重新从位置 0 开始。

0 1 2 3|4 5 6 7

RoPE 或其他位置编码看到的必须是原始序列位置，否则第二个 chunk 会被误认为一条新 Prompt。

Causal Mask 不截断展开例子

第二轮 Query 不仅能看本 chunk，还能读取边界左侧全部合法历史。

K0…K3+K4…Ki

对全局位置 i 的 Query，规则仍是只能读取满足 j ≤ i 的 Key；chunk 边界不会增加一条新的 mask。

Q4 可读取
K0K1K2K3K4K5K6K7
Q7 可读取
K0K1K2K3K4K5K6K7

检查点：Q7 能看到 K0–K7，而不是只有 K4–K7；其他 sequence 的 KV 仍然不可见。

正确性结论：只要 KV 状态、全局 position 和 causal visibility 与一次性 Prefill 一致，切块就没有改变模型的依赖关系。不同 kernel 或浮点归约顺序仍可能产生非 bitwise-identical 的微小数值差异。

2. Mixed Batching：让 Decode 与 Prefill Chunk 共享一次 Forward

切块本身只创造了更多调度边界。Scheduler 可以在两个 chunk 之间插入一轮纯 Decode，这叫 interleaving；更进一步，它还可以把正在运行请求的 Decode token 与某条等待请求的 Prefill chunk 放进同一个 batch、同一次 model forward，这才是 Mixed Batching。

一个常见的 decode-first 组批方式是：先统计本轮所有 running request 需要的 Decode token，为它们保留 token budget；再把剩余 budget 填入一个或多个 Prefill chunk。这样 Prefill 继续推进，而流式请求不必整轮停下来等它。

one forward = {Decode tokens} ∪ {Prefill chunk tokens}

这才是 Mixed Batching 的严格含义。常见 decode-priority 策略先放入 running Decode，再用剩余 token budget 装 Prefill chunk；真实 Scheduler 还要检查 KV capacity、priority、CUDA Graph 和功能兼容性。

为什么混在一起还可能提高 GPU 效率

两类工作对硬件的压力互补。Mixed Batching 不只是减少排队，还可能提高整个 forward 的有效算术强度。

Prefill chunkcompute-heavy

同时处理许多 Query，权重能被多个 token 复用，GEMM 较大，更容易充分使用 Tensor Core。

Decode tokensmemory-heavy

单条序列每轮只有一个 Query，小 batch 时计算单元利用率低，而模型权重与长历史 KV 的读取成本突出。

Mixed forwardbetter balance

把 latency-sensitive Decode token 拼到 compute-dense Prefill chunk 中，公共线性层能在一次更大的 token batch 中执行并摊薄权重读取；在合适规模内，加入 Decode 的增量代价可能较小。[1]

不是字面上的“计算和 I/O 同时跑”。框架通常统一组织 token metadata，线性层可合并成更大的 GEMM，而 Prefill attention 与 Decode attention 仍可能走不同 kernel。最终收益取决于 kernel 支持、batch shape、KV 访问和 graph capture。

执行模式一个 forward 里有什么能解决什么
Full Prefill整条 Prompt Prefill。路径简单，但重新调度窗口最长。
Chunked, non-mixed只有 Prefill chunk，或只有 Decode。Decode 能在 chunk 边界插入，但每个 Prefill forward 期间仍会等待。
Chunked + mixedDecode token 与 Prefill chunk 共存。利用剩余 token budget 持续推进 Prefill，同时保护 Decode cadence。
两件事不要混为一谈Chunking 决定“多久把控制权交还 Scheduler”；Mixed Batching 决定“下一轮是否让 Prefill 和 Decode 一起执行”。开启前者并不自动意味着已经实现后者。

3. Multimodal：Image / Video Token 怎样进入 Chunked Prefill

多模态请求并不是把 JPEG 像素或整段视频直接塞进 LLM。通常先对图片做 resize / tile，对视频做抽帧，再由 vision encoder 产生视觉特征；processor 随后把 Prompt 中的占位符扩展成一段 visual embeddings。常规 Chunked Prefill 切的是 LLM 侧已经展开的 token / embedding 序列，不是原始图片、视频帧，也不自动切分 vision encoder。

因此多模态路径至少有三种不同的“粒度”：媒体预处理粒度、vision encoder 的 item / cache 粒度、LLM Prefill 的 token budget。图片分辨率、tile 数，或视频的采样帧数 × 每帧视觉 token 数，都可能让一个看似很短的文本 Prompt 膨胀成长 Prefill；视频尤其容易产生突发的大段视觉 token。

ADDITIONAL READING深度优化：Long Context 与 PP——把固定 Token Chunk 变成固定时间附近的 MicrobatchSGLang DynamicChunkSizer、延迟模型与 PP cadence

真正需要优化的不是“长上下文是什么”，而是同样大小的 chunk 在 Prompt 后半段越来越慢。设已经缓存的历史长度为 H，下一段新 token 数为 x。Attention 需要让这 x 个 Query 读取长度约为 H+x 的 Key/Value，因此仅看 attention 主项，增量工作近似随 x(H+x) 增长。固定 x 时，H 越大，单轮 latency 越长。

这会同时伤害两个目标：单轮不可重新调度窗口重新变长，Decode ITL 又开始抖动；在 PP 中，连续 microbatch 的执行时间越来越不均匀，前后 stage 会围绕慢 microbatch 等待。优化目标因此应从“每轮固定 4K token”改成“每轮尽量接近同一个目标 latency”。

SGLang 使用的经验 Latency Model f(l) = a·l² + b·l + c ΔT(H, x) = f(H+x) − f(H) = a·x² + (2aH+b)·x 选择 x，使 ΔT(H, x) ≈ T_target

f(l) 不是理论 FLOPs 公式，而是对当前模型、dtype、kernel 和 GPU 的实测 Prefill latency 拟合。随着 H 增大，满足同一 T_target 的正根 x 会自然变小。

为什么这会优化 Long Context

第一，Query-side activation、临时 workspace 和每轮 admission work 由 x 限制，不再随整条输入长度一次性膨胀。第二，history 越长时自动减小 x，把 late chunk 的延迟拉回目标附近，避免它重新形成一个很长的不可抢占窗口。第三，page/tile 对齐减少碎片与不友好的 kernel shape。

它没有压缩最终 KV Cache。完整 Prompt 的每层 K/V 最终仍要保存，容量仍近似随总上下文线性增长；它控制的是每轮新增工作和临时内存。更小的 late chunk 还会增加 iteration、launch 和 metadata 开销，因此源码设置平滑、下限和对齐，而不是无限缩小。

为什么这会优化 PP Bubble

PP 需要多个 microbatch 同时处在不同 stage。理想化的 forward-only 流水线中，若有 p 个 stage、m 个等时 microbatch，利用率近似为 m/(m+p−1)。Chunking 增加 m；动态 sizing 进一步让连续 microbatch 的时长更接近，从而减少由 late chunk 变慢造成的额外 imbalance bubble。

重要实现事实：当前 SGLang 不是“按最慢 Stage 闭环控制”在本文固定的 commit 中，PP0 profile synthetic Prefill，样本广播给所有 rank，并由每个 rank 拟合同一个模型。它通过统一、近似恒时的 chunk 改善 PP cadence；并没有分别测量所有 stage 后针对 bottleneck stage 做在线反馈控制。[4]
它重点减少

长历史导致的 iteration latency 漂移、单轮 activation/workspace 峰值、PP microbatch 时长不均带来的额外 bubble。

它不能消除

PP 固有的 fill/drain bubble、层切分不均、跨 stage 通信、最终 KV 容量，以及 kernel/backend 本身的效率问题。

它可能付出

更多 forward launch、调度与 metadata 开销；如果预测模型偏离线上 mixed workload，目标 latency 也未必准确。

上线验证

同时观测 chunk latency 分布、各 PP stage time、pipeline idle、p99 ITL、长 Prompt TTFT、tokens/s 与 KV/activation headroom。

03 / IMPACT & LIMITS

Chunked Prefill 解决哪些问题，能够优化哪些指标

它最直接的作用是限制一次 Prefill 占用 GPU 的时间和资源峰值。由此可能改善 Decode 尾延迟、Goodput 与 PP 利用率，但不会减少模型必须完成的总计算或最终 KV 容量。

评价 Chunked Prefill 时，需要把三类变化分开：它直接控制的单轮执行边界；在正确调度和 Mixed Batching 下可能改善的系统指标；以及无论怎样切块都不会凭空消失的模型工作。

问题或指标开启后的典型方向为什么会变化成立条件与边界
主要解决的问题与可能改善的指标
Decode p95 / p99 ITL、TPOT通常下降长 Prefill 被拆成较短的不可抢占窗口，Decode 更快获得下一次调度机会。chunk 必须足够小；Scheduler 必须在边界处真正优先安排或混入 Decode。
ITL 波动与 Generation Stall通常下降单个长 Prompt 不再一次占据一个很长的 forward，干扰半径受到限制。若 chunk 仍很大，或多个 Prefill 连续占满预算，尖峰仍会出现。
单轮执行时间峰值下降且更可控每轮最多处理一个受限大小的 Prefill chunk，Scheduler cadence 更可预测。Long Context 下应按 history 动态 sizing；固定 token chunk 的耗时仍会逐渐增长。
Activation / Workspace 峰值通常下降Query-side 中间状态和临时工作区由本轮 chunk 大小限制，而不是由整个 Prompt 一次决定。具体峰值依赖 Attention backend、CUDA Graph、并行方式和 batch composition。
吞吐与 GPU 利用率可能提高Mixed Batching 可让 memory-heavy Decode 与 compute-heavy Prefill chunk 共享 forward，并减少空闲 token budget。单纯切块不保证吞吐提升；chunk 太小会增加 launch、metadata 和调度开销。
SLO Goodput常比 Raw Throughput 更值得关注ITL 尾部降低后，同一容量下可能有更多请求同时满足 TTFT / ITL SLO。必须按真实输入长度、输出长度、到达率和并发分布测试。
PP Imbalance Bubble可能下降更多且 latency-shaped 的 microbatch 更容易维持稳定 pipeline cadence。要求多个 microbatch in-flight；无法消除 fill/drain、通信和层切分不均。
长 Prompt TTFT可能升，也可能降更好的排队与组批可能缩短等待；但更多 iteration、launch 和 Decode 插队也可能延迟首 token。不能把 TTFT 写成必然收益，必须同时观察 p50 与 p99。
Chunking 本身不会改变或消除的东西
理论总 FLOPs / Attention 依赖数量级基本不变后面的 chunk 仍然需要读取完整合法前缀；只是把同一依赖图分多轮执行。kernel shape、padding 和 fusion 会改变实际 wall time，但不代表模型工作被删除。
最终 Prompt KV Cache 容量基本不变完整 Prompt 的每层 K/V 最终仍需保存，容量仍随上下文长度增长。Chunking 降低的是单轮临时峰值；KV 压缩、量化或 offload 是另一类优化。
模型权重与输出依赖关系不变KV、全局 position 与 causal mask 正确时，Chunked Prefill 保留与完整 Prefill 相同的逻辑依赖。不同 kernel 和浮点归约顺序可能造成非 bitwise-identical 的微小数值差异。
TP / PP 的基础通信不会消失TP collective 与 PP stage 间 activation 传输仍然存在；Chunking 主要改变消息粒度和时间安排。网络带宽不足或 stage partition 不均仍需独立优化。
判断是否值得开启

不要只比较平均 tokens/s。至少同时看 p95/p99 ITL、TTFT 分布、SLO goodput、单轮 latency 峰值、activation / workspace headroom，以及 PP stage idle。Chunked Prefill 的核心价值是重新分配工作发生的时间，并限制单轮峰值，而不是减少模型总工作量。

Takeaway：从“单个 Prefill 最快”转向可接受的 Operating Point

完整 Prefill 倾向于优化这一条 Prompt 自己最快完成；Chunked Prefill 把优化目标改成：在 TTFT、Decode ITL、在线吞吐和显存峰值之间找到满足业务 SLO 的 operating point。通常的选择规则不是“chunk 越小越好”，而是在满足 p99 ITL 与显存约束的前提下，选择尽可能大的 chunk，减少额外 iteration 和 launch 开销。

04 / DESIGN & IMPLEMENTATION

四个 Policy 如何共同决定一次 Chunked Prefill

Chunk Size 只回答“本轮最多做多少”。一个可上线的 Scheduler 还必须决定谁能进入、Prefill 与 Decode 如何组批，以及未完成请求何时续跑。

下面的四个 Policy 是工程职责的拆分，不要求框架内部真的存在四个同名类。它们必须在同一次 scheduling iteration 中联合决策：前一个 Policy 的输出，会成为后一个 Policy 的预算或约束。

POLICY 01

Chunk Sizing这条 Prefill 本轮具体推进哪个 token 区间？

输入信号

未计算 token 数、history / prefix length、静态 cap、目标 iteration latency、page / tile 粒度、当前 batch token budget、上下文上限。

输出决策

为请求选择 extend_range=[start,end)；判断本轮是 middle chunk 还是 last chunk，并确定需要预留的 KV pages。

必须守住

0<x≤remaining；位置连续；对齐后仍不越过 context limit；预算按实际新 token 数扣减，不能按原 Prompt 长度重复扣。

观测指标

chunk latency 分布、每请求 chunks 数、p99 ITL、长 Prompt TTFT、activation peak、kernel shape 与 launch overhead。

典型失败

过大：不可抢占窗口、ITL spike、PP imbalance 和单轮显存峰值回升。过小：iteration、launch、metadata 与调度成本吞掉收益。

SGLang 映射

chunked_prefill_size 给出基础 cap；PP dynamic path 根据 history_len 预测下一段大小，再做 page_size / 64 对齐、下限和容量裁剪。

POLICY 02

New-work Admission在已有 Decode 与 continuation 之外，哪些新 Prompt 可以开始？

输入信号

waiting queue 顺序、priority / arrival time、prefix-cache hit、待计算 input tokens、当前与未来 KV 预算、request-slot、LoRA / grammar 等兼容条件。

输出决策

生成本轮 can_run_list，或因 token、KV、slot、tile budget 用尽而停止继续接纳；必要时选择可被抢占的低优先级工作。

必须守住

KV allocation 与 token budget 同时可行；cache match 后重新计算真实 extend length；拒绝请求时回滚临时锁、slot 或 staged metadata。

观测指标

queue age、admission reason、prefix hit length、KV 使用率、实际 Prefill batch size、被跳过和被抢占请求数。

典型失败

只按 FCFS 会放弃高价值 cache hit；只追求短请求或 cache hit 会饿死长 Prompt；只检查本轮 input budget、忽略未来 Decode KV，会出现过度接纳和后续 retraction。

SGLang 映射

SchedulePolicy.calc_priority() 先排序；PrefillAdder 同时维护 remaining input/chunk token、KV memory budget、request slots 与 backend tile budget。

POLICY 03

Batch Composition本轮是 Prefill-only、Decode-only，还是 Mixed Forward？

输入信号

running Decode 数、batch token budget、已选 Prefill chunks、mixed 开关、CUDA Graph shape，以及 logprob、input embeds、beam、spec decode 等 feature matrix。

输出决策

选择 forward mode；常见 decode-first 做法先把每条 running request 的一个 Decode token 放入，再用余量装 Prefill token。

必须守住

每条 Decode row 仍只有一个新 token；Prefill rows 保持各自 prefix / extend length；合并后 input、position、KV location 与输出拆分必须一一对应。

观测指标

Mixed forward 占比、每轮 Decode / Prefill token 数、CUDA Graph hit、graph fallback 原因、kernel time、ITL 与 tokens/s。

典型失败

允许 mixed 但 kernel 或 metadata 路径不支持，会出现 shape mismatch、错误采样或 graph fallback；Decode reserve 太大使 Prefill 不前进，太小则重新制造 ITL spike。

SGLang 映射

PrefillAdder 用 num_mixed_decode_tokens 预扣 input 与 chunk budget；满足兼容条件后，mix_with_running() 把 Decode row 转成 1-token extend，并把 forward mode 设为 MIXED。

POLICY 04

Continuation & Preemption已经做了一部分、占着 KV 的 Prompt 下一轮何时继续？

输入信号

partial request 的 prefix / extend progress、已占 KV、defer 次数与 age、等待队列 priority、free pages、abort / pause 状态、PP microbatch 状态。

输出决策

优先续跑、允许暂缓、提高 age、抢占其他请求，或在内存压力下 retract 并重算；last chunk 完成后才进入正常 sampling / Decode。

必须守住

continuation 不能丢失或重复 KV；中间 chunk 不提前 sample；abort、pause、weight update 和 PP 跨 microbatch 路径都必须安全释放或保留资源。

观测指标

continuation wait time、连续 defer 次数、chunks / request、retract 与 recompute tokens、KV residency、partial request age。

典型失败

新请求不断插队会让 partial Prefill 长期持有 KV 却得不到首 token；过度保护 continuation 又会压制新请求公平性。错误清理还可能导致 KV leak 或 double free。

SGLang 映射

chunked_req 显式保存 continuation；Scheduler 在接纳新请求前先尝试 add_chunked_req()，并更新 inflight_middle_chunks 与 contains_last_prefill_chunk。

四个 Policy 必须联合调优

Size 决定单轮成本上限；Admission 决定谁获得资源；Composition 决定 Prefill 与 Decode 是否共享 forward；Continuation 决定 partial request 会不会饥饿。只扫描 chunk size，无法解释由 queue priority、KV admission 或 mixed compatibility 导致的问题。

四个 Policy 不是并列开关，而是一条反馈回路

这段不是第五个设计原则，而是在回答“前面四个 Policy 怎样一起工作”。它们也不是严格的一次性流水线：Batch Composition 要先声明 Decode reserve，Admission 才知道还剩多少 Prefill budget；执行结束后，Continuation 又把 partial request 带回下一轮。因此更准确的关系是“前馈决策 + 跨轮反馈”。

三个最重要的参数分别控制不同层次

参数控制什么不要误解成什么
--chunked-prefill-size单个 Prompt chunk 的最大 token 数；-1 表示关闭。不是整轮 Prefill batch 的总 token budget。
--max-prefill-tokensPrefill batch 的总输入 token 预算。不是每条请求都能各自使用这么多 token。
--enable-mixed-chunk允许 Prefill 与 Decode 在一个 batch 中混合。不是开启 chunking 本身；在核对的 commit 中该字段默认关闭。
--enable-dynamic-chunkingPP 场景下按 profile 得到的延迟模型动态选择 chunk size。不是对所有非 PP 部署都自动更优。

PrefillAdder 的价值在于让预算在一个地方闭合。Mixed chunk 开启后，running Decode token 会从可用 input/chunk budget 中扣除，同时 KV allocator 还要为这些 mixed token 保留空间。只改 chunk size 而没有同步修改这几种 accounting，容易得到“看似能跑，压力下错账”的实现。

DynamicChunkSizer 为什么只看 token 数还不够

同样是 4K 新 token，当历史长度为 0 和历史长度为 64K 时，Attention 需要读取的前缀完全不同，forward latency 也不会一样。SGLang 的 PP dynamic chunk path 会先 profile Prefill latency，用近似二次模型拟合序列长度与耗时，再根据当前 history length 预测下一段大小。目标更接近“固定时间的 chunk”，而不是机械地固定 token 数。[4]

与 Speculative Decoding 的关系Speculative Decoding 主要优化 Decode。开启 mixed chunk 后，具体 speculative algorithm 必须支持相应组合路径；修改配置时应验证 draft/verify metadata、lookahead token、CUDA Graph 和最后一个 Prefill chunk 的处理，不能只确认服务成功启动。
06 / VLLM

vLLM：用每轮 Token Budget 自然形成 Chunk

vLLM V1 的核心不是单独维护一个固定 chunk 队列，而是让每条请求追赶 num_computed_tokens，并把本轮可推进量裁剪到全局 token budget；装不下的 Prefill 会自然留到下一轮。

同一个机制，不同的状态表达

每轮开始时，Scheduler 建立 token_budget 与 input_budget。它先扫描 running 请求，再扫描 waiting 请求；对每条请求计算“尚未追上的 token 数”，然后用剩余预算裁剪。若 KV allocator 能分配新 blocks，请求就进入本轮输出；否则会按 policy 尝试 preempt，或停止继续接纳。

因此，vLLM 的 partial Prefill 不需要等价于 SGLang 的单独 chunked_req 槽：请求已经有一部分 num_computed_tokens，但仍未追上 Prompt 末尾，它就作为 in-progress work 在后续 iteration 继续。官方 V1 文档把默认策略概括为：优先安排 pending Decode，再用 max_num_batched_tokens 的余量装 Prefill；装不下的 Prefill 自动切块。[8]

# 每轮共享预算；RUNNING 中既可能有 Decode，也可能有 in-progress Prefill
token_budget = self.max_num_scheduled_tokens
input_budget = self.scheduler_config.max_num_batched_tokens

for request in self.running:
    num_new_tokens = request.num_tokens_with_spec - request.num_computed_tokens

    if 0 < long_prefill_token_threshold < num_new_tokens:
        num_new_tokens = long_prefill_token_threshold

    # 关键：本轮剩多少预算，就最多推进多少；余下部分留到下一轮
    num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)
    new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens, ...)

    if new_blocks is not None:
        num_scheduled_tokens[request.request_id] = num_new_tokens
        token_budget -= num_new_tokens
        input_budget -= num_new_tokens + draft_slots

# WAITING 请求同样受 request_token_budget 约束
if not enable_chunked_prefill and num_new_tokens > request_token_budget:
    break
num_new_tokens = min(num_new_tokens, request_token_budget)

主要旋钮怎样读

参数真正控制什么典型方向
--enable-chunked-prefill允许 Prefill 在单轮预算装不下时分多轮推进；V1 在可用时默认开启。关闭后，完整 Prefill 必须能装入 batch token budget。
--max-num-batched-tokens每个 iteration 能调度的总 token 数，是最重要的 operating-point 旋钮。较小通常偏向 ITL；较大通常偏向 TTFT 与吞吐。官方文档建议小模型/大 GPU 追吞吐时可测试大于 8192。
--max-num-seqs每轮序列数与 runner / CUDA Graph 容量边界。它约束并发 shape，不等价于 token budget。
--long-prefill-token-threshold存在竞争请求时，限制单条长 Prefill 本轮最多推进多少 token；单独运行时不施加该 cap。用于减少一个长 Prefill 吞掉全轮预算的风险；默认 0 表示不额外限制。[10]
读 vLLM 源码时抓住一个统一抽象num_computed_tokens 追赶当前请求需要计算的 token 数。这个差值既能表达 Chunked Prefill，也能容纳 prefix caching、speculative decoding 和恢复后的请求；Chunking 只是“本轮 budget 不允许一次追完”时自然出现的结果。[9]
07 / PERFORMANCE EVIDENCE

已有性能评估：收益在哪里，代价在哪里

这里保留原论文图，而不只摘录倍数。先确认模型、GPU、并行方式、数据集与 SLO，再判断结论能否迁移到自己的 SGLang 部署。

先正确阅读 Sarathi-Serve 的数字

Sarathi-Serve 论文把 Chunked Prefill 与 stall-free batching 结合，在尾延迟约束下比较 serving capacity。论文报告：Mistral-7B 单张 A100 相对当时的 vLLM 达到 2.6× capacity；Yi-34B 在两张 A100、TP=2 下最高 3.7×；Falcon-180B 在八张 A100、PP=2、TP=4 且使用普通以太网时，端到端 capacity 最高 5.6×。可直接对照原文 Figure 10、Figure 11 与 Figure 13。[1]

这三个数字不是“Chunked Prefill 单项加速倍数”，也不应拿来预测当前 SGLang。它们包含 Scheduler、hybrid batching、并行策略和特定 SLO 的共同效果，比较对象也是论文实验时期的系统版本。

Chunk 越小，额外开销越明显

论文在 Yi-34B、TP=2 的 Prefill 消融中报告：chunk=512 时总 Prefill runtime 的额外开销最高约 25%；chunk=2048 时几乎可以忽略。这个数字只适用于该实验，但方向非常重要。

Chunking 与 Hybrid Batching 需要配合

论文消融显示，chunk-only 会因为切片低效而增加 TTFT；hybrid-only 仍可能被完整长 Prefill 拉高 TBT；两者结合才同时改善两个维度。

公开评估给出的不是“把参数设成 2048”，而是一个实验假设：存在一个足够小、可以保护尾延迟，又足够大、不会被切片开销吞噬的区间。

SGLang 当前默认值只是硬件启发式

在核对的 SGLang commit 中，如果用户没有显式设置，memory hook 会按可见 GPU 显存给出分档起点：低于 20 GiB 使用 2K；20–60 GiB 使用 4K；60–160 GiB 使用 8K；160 GiB 及以上使用 16K。代码注释明确说明这是利用“更大显存通常意味着更强 GPU”的启发式，同时还用于估算 activation 与 CUDA Graph 需要预留的内存。它不是 workload-aware 的性能最优解。[5]

SGLang 官方调优文档提供了更直接的故障导向建议：如果 OOM 发生在 Prefill，可以把 --chunked-prefill-size 降到 4096 或 2048；这样会节省内存，但会降低长 Prompt 的 Prefill 速度。[6]

把论文趋势映射到 SGLang 参数

下面保留“现象 → 首选旋钮 → 同时排查”的映射，但不在这里规定一套固定调优流程。论文的 token budget 不是 SGLang 参数的逐字等价物；迁移时应分别看 --chunked-prefill-size、--max-prefill-tokens 与 --enable-mixed-chunk。

观察到的现象优先尝试同时确认
p99 ITL 有明显尖峰减小 chunk；启用/检查 mixed；提高 Decode reserve。尖峰是否与长 Prefill 到达时间相关，是否发生 graph fallback。
长 Prompt TTFT 明显变差增大 chunk 或总 Prefill budget；减少无谓 defer。Scheduler/launch overhead、continuation starvation、cache hit 分桶。
Prefill OOM把 chunk 降到 4K/2K；降低 mem_fraction_static。activation headroom、CUDA Graph buffers、实际解析出的配置。
队列很深但 GPU 利用率低检查 admission、max_prefill_tokens、KV capacity 与 CPU scheduler。不能只继续增大 chunk；可能根本不是 Prefill 粒度瓶颈。
PP stage latency 波动大尝试 --enable-dynamic-chunking。各 stage latency、in-flight microbatch、通信和层切分不均。
开启 Mixed 后结果异常回退 Mixed，逐项加回 feature。Spec decode、logprob、beam、LoRA、multimodal、CUDA Graph。
最终选择规则在不 OOM、功能组合正确并满足 Decode p99 ITL 的前提下，选择尽可能大的 chunk；随后再调总 Prefill budget、Mixed 和 continuation policy。这样可以减少切片轮数，又不会让长 Prefill 重新占住过长的执行窗口。
